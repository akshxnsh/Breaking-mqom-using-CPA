# What `live_recovery_demo.py` Does — Step by Step

This explains the demo script in plain language: what happens on screen, and
what's actually being computed underneath. Nothing here is new research — the
script just runs the project's existing, already-validated attack code
(`candidate_c/`, `candidate_b/`, `assembly/`) and narrates it.

**Important:** everything below is a simulation. No real chip, no real
measurement, no real MQOM signing ever happens. All "signatures" and "power
readings" are random numbers generated by the script itself.

---

## Step 0 — Make up a secret key

```python
x = random 48 bytes
```

The script picks 48 random numbers (0–255) and calls that our pretend secret
key `x`. This is the answer we're trying to recover — but the attack code
never gets to see it directly.

---

## Attack 1 — Recovering the suffix (32 bytes)

**What it's based on:** every time MQOM signs something, it publishes a
number called `Δx` (delta-x) that changes each time. The secret byte and this
public number get combined (`x XOR Δx`), and that combination is assumed to
leak through power usage.

**What the script does, concretely:**

1. **Fake 300 signatures at once.** It generates a table of 300 random
   numbers per byte (representing 300 signing events) and XORs each one
   against the real secret byte to get the public `Δx` values.
2. **Fake the power reading for each one.** It counts the 1-bits (Hamming
   weight) of each hidden combined value and adds a bit of random noise —
   this stands in for "how loud the leak was."
3. **Guess every possible byte value (0–255).** For each guess, it predicts
   what the power readings *should* look like if that guess were correct,
   across all 300 fake signatures.
4. **Compare predictions to the fake readings.** It checks how closely each
   guess's predicted pattern matches the actual fake readings — this
   "closeness" is called correlation.
5. **Pick the guess with the strongest match.** That becomes the recovered
   byte.
6. **Watch for the mirror-twin tie.** Two guesses that are exact bit-flips of
   each other (e.g. `0x44` and `0xBB`) always score equally strong — the
   script keeps the *sign* of the match (not just its strength) to tell them
   apart.
7. **Repeat for all 32 suffix bytes.**

---

## Attack 2 — Recovering the prefix (16 bytes)

**What it's based on:** inside a single signature, each secret byte gets
multiplied by thousands of different public numbers as part of MQOM's
verification math. No `Δx` trick is available here — a different byte of the
key is hidden from that channel entirely.

**What the script does, concretely:**

1. **Fake ~1,800 public multipliers** for one secret byte (representing all
   the multiplications that byte takes part in within one signature).
2. **Fake the power reading for each multiplication** the same way as
   before: Hamming weight of the result, plus noise.
3. **Guess every possible byte value**, predict what the readings should
   look like for each guess, and correlate.
4. **Pick the strongest match** as the recovered byte — unless the strongest
   match is suspiciously weak (below a threshold), in which case the byte is
   **flagged** instead of guessed. A real byte of `0x00` produces no useful
   signal (multiplying by zero always gives zero), so this is a known,
   self-announcing blind spot rather than a silent wrong answer.
5. **Repeat for all 16 prefix bytes.**

---

## Assembly — Gluing the two halves together

1. **Stick the prefix and suffix guesses together** into one 48-byte
   candidate key.
2. **Handle leftover uncertainty.** Two small ambiguities can remain:
   - The suffix might be exactly bit-flipped (a "global polarity" issue).
   - Any flagged prefix byte is still unknown.
3. **Try the small number of remaining possibilities** (flipped vs.
   not-flipped, each flagged byte at every possible value) against MQOM's
   own public equations — 48 equations that the real key is guaranteed to
   satisfy.

---

## Certification — Checking the final answer

1. **Plug the assembled candidate into all 48 public equations.**
2. **If all 48 pass,** that candidate is accepted as the recovered key, `x̂`.
3. **Compare `x̂` to the real `x`** (which the script secretly kept track of
   from Step 0) to confirm they're identical.

---

## Why it all happens instantly

Every step above is just arithmetic on small tables of numbers — not a real
device being triggered, measured, or waited on. A modern computer performs
millions of such calculations per second, and the tool used here (NumPy)
does each step on an entire table of numbers at once rather than one value
at a time. That's the whole reason the "attack" finishes in a fraction of a
second: it's simulating the *math* of a leak, not the *physical process* of
collecting one.
